# Classifying a slow pytest file

Use after ranking files (SKILL.md Step 3). Look at the phase (`setup` / `call` / `teardown` in `--durations`) and the shape before proposing a fix.

| Signature | Cause | Action |
| --- | --- | --- |
| Every test in the file pays ~the same seconds in `call`; a helper builds a heavy object (`DagBag(...)`, app, schema) | Repeated construction per test or per helper call | Reuse the repo's session fixture → `pytest-shared-setup.md`. Grep the whole test tree for the same constructor: the pattern usually recurs in sibling files |
| One test per runner shows a huge `setup` (tens of seconds) and the rest of the file is fast | One-time session fixture (DB container start, ORM `create_all`/`drop_all`) paid by whichever test first requests it | Not that file's fault: confirm it is the first requester in each leg's `-v` log (alphabetical order usually decides), and say that deleting or skipping it only moves the cost to the next requester. Count how many *separate* session schemas/containers each runner builds; duplicates are the saving, and whether they can share a DB is a hypothesis to test, not a fact |
| Narrowing a test fixture's `create_all(tables=...)` does not reduce setup | The code under test itself calls `Base.metadata.create_all(...)` at runtime, so the first call recreates the full schema on the fresh test DB | The real fix is in production code (narrow its `create_all` to the tables it uses, which also cuts per-call existence queries in prod). Offer it next to the test-only alternative (reuse an existing session DB for one of the connections); once chosen, add it as its own commit on the open PR of the same work stream and name the prod-behavior change in the PR body (split it out only if the user asks). Recipe below |
| Few tests, long `call`, cProfile top line is `select.kqueue.control` / `select.epoll.poll` / `time.sleep` | Real sleeping (retry backoff, rate limiter, throttle) the test meant to disable | Find which sleep escaped the patch (below) |
| Wall time ≫ CPU (`/usr/bin/time -p`: e.g. 46 s real, 1.4 s user), one test takes an exact round time (`30.00s`) and another a sum of doublings (`14s` = 2+4+8) | A literal wait in product code the test cannot reach: a `thread.join(timeout=30.0)` the test drives to expiry, or a backoff `wait(...)` in a caller loop outside the helper the test patched | Name the value in product code with the same number (`<NAME>_JOIN_SEC = 30.0`, one `_backoff(attempt)` function shared by every retry site), monkeypatch the names in the test, delete any hack that swaps `Event.wait` on an instance, and pin the real schedule with one plain assertion test (`[backoff(a) for a in 1..8] == [1, 2, 4, …, 60]`) since the retry tests no longer exercise it. Recipe below |
| CPU-bound, every test ~1–4 s in `call`, cProfile `cumtime` top is `DagRun.update_state` / `task_instance_scheduling_decisions` / `_get_ready_tis` under a test helper looping `update_state` | The test drives a real Airflow scheduling loop over a large DAG on purpose (trigger-rule proofs); the DAG itself is built once (module fixture) | Intended cost — do not call it re-parsing until cProfile shows `DagBag`/DAG-factory time. A semantics-free lever first: when several tests re-run the same simulation (an on/off pair per case plus a separate test re-simulating one case), cache the result per (DAG, case) at module scope — but a module cache lives in one pytest process, so under a sharded CI (`pytest-split --splits N`) it saves nothing when the re-simulating test and the parametrized case land on different shards (check each test's leg in the `--durations` lines of the PR run). Prefer folding the extra assertion into the matching parametrized case so the dedupe holds on every split, and never quote the local saving as the CI saving until the PR run shows both consumers in one leg. The bigger lever (`dag.partial_subset` around the asserted tasks) changes what the run-state assertion proves, so it is the test owner's decision; offer it with the file's own "only these edges change" test as the argument, or list it out of scope with that reason. Before offering it, profile one parametrized case and quote the share under `DagRun.update_state` / `are_dependencies_met` (call counts × rounds): that number shows the test-side code has nothing left to trim. Then size the subset that keeps the claim: descendants of the changed tasks plus every ancestor of those descendants (`get_flat_relatives(upstream=False/True)`). When that is ≈ the whole DAG, no subset preserves "every task ends in the same state", and a descendants-only subset (`include_upstream=False`) silently drops the cases whose injected failure sits upstream of the change — report those counts instead of offering the subset as a speedup. Ship the semantics-free part, and put the subset question to the owner in the PR body (reviewer = owner) with an offer to add it to the same PR on a yes — not as a separate PR or issue |
| A function-scoped fixture pays 2–4 s `setup` per test; it builds a tiny DAG and calls `DagBag(include_examples=False).bag_dag(...)` / `sync_to_db()` | `DagBag()` without `dag_folder` fills itself from `DAGS_FOLDER`, which the test conftest points at the repo's real DAG directory — every test parses every DAG | Pass `dag_folder=os.devnull`. Then check generated ids: a `dag_id` built from a seconds timestamp + `id(object())` stayed unique only because each setup took seconds; once fast it collides (`UNIQUE constraint failed: dag_run.dag_id, dag_run.run_id`), so use `uuid4().hex` |
| One CPU-bound test that regenerates a committed artifact (column lineage, schema dump) and compares it; cProfile `cumtime` under `sqlglot.lineage.lineage` → `Select.select` → `_apply_list_builder` | sqlglot `lineage()` defaults to `trim_selects=True`, which deep-copies the whole SELECT for every node of every column's graph (thousands of copies of large CTE queries) only to make node labels | If the caller reads only leaf tables/columns and `node.source` star checks (not the trimmed SELECT text), pass `trim_selects=False` in the production helper — usually two orders of magnitude. The artifact-equality test itself proves output is unchanged; add a positive control by deleting one field from the committed artifact and confirming the test fails, then restore |
| Wall ≫ CPU, cProfile `tottime` top is `_ssl._SSLSocket.read` / `do_handshake` / `socket.connect` under `botocore` (or `requests`/`urllib3`) | Tests reach a real cloud API with whatever credentials the environment has — CI usually configures a test-account role, so the calls succeed or fail slowly instead of erroring fast; code that "falls back on any read error" hides it | Count calls per test with `scripts/boto_call_counter.py` (pytest plugin), confirm the tests pass with credentials removed (`env -u AWS_PROFILE AWS_CONFIG_FILE=/dev/null AWS_SHARED_CREDENTIALS_FILE=/dev/null AWS_EC2_METADATA_DISABLED=true pytest ...`), then stub the client factory in the shared fixture (recipe below). It is a determinism bug as much as a speed one: the tests depend on live account state |
| `dag.test()` tests wait ~1 s per scheduling round; cProfile shows `time.sleep` called from `airflow/models/dag.py` `test` | Airflow's `dag.test()` loop sleeps 1 s whenever non-finished tasks exist but none is scheduled — a deferrable operator (trigger) or a retry wait | Patch only the name the loop looks up, in the module the method is defined in (`sys.modules[DAG.test.__module__]` — Airflow 2 `airflow.models.dag`, Airflow 3 `airflow.sdk.definitions.dag` with `import time` inside the method, so there is nothing to patch there), after checking which other `time.` functions that module calls; never `patch("time.sleep")` globally — other threads in the pytest process then record or skip their own sleeps. Before wiring it, run the files once with an experiment plugin that counts the skipped sleeps: the count must equal the original sleep count — a jump means the loop now busy-spins on a time-based wait (retry delay) and the patch saves nothing |
| Scheduler-simulation tests (round loop that commits every round) run several times slower per test on Linux CI than locally on macOS — a CI/local ratio well above the suite's usual one | Unproven. sqlite fsync is a candidate (the test metadata DB is a sqlite file; macOS `fsync` does not flush): in a Linux container `PRAGMA synchronous=OFF` cut these files ~35%, yet on the GitHub runner the same tests kept their `--durations` with it applied — the runner's cost is elsewhere (CPU, not measured) | Do not ship a test-infra toggle on a container result alone. If you try one, put a target in the PR body ("file X's per-test `--durations` drops vs the same-base push run"), read the first PR run's `--durations` lines for those tests, and revert the commit on the branch when they did not move. A listener's effect can be checked with a throwaway test printing `PRAGMA synchronous` through `airflow.settings.Session()` (`0` applied, `2` not) — that proves it applied, not that it helps |
| Wall ≫ CPU, cProfile top is `socket.recv_into` under a MySQL driver | DB round trips to a container (per-test truncate/insert loops); much slower against Docker Desktop than on a Linux CI runner | Check the CI per-file seconds before acting — local numbers overstate it; batch the statements only if CI shows the cost |
| Lock-wait / timeout tests that hold DB locks on purpose | Intended server-side timeout | Leave it; say so in the report |
| Each test pays ~1s `setup` for a function-scoped DB fixture | New database per test | Candidate for a session schema + per-test truncate, only if the repo already has that pattern |

## Finding an escaped sleep

- `python -m cProfile -s tottime -m pytest -p no:cacheprovider -q <file>::<test> | grep -A14 "Ordered by"`: event-loop or sleep wait time at the top with ~N calls of ~retry-wait seconds confirms real waiting.
- `patch("asyncio.sleep", ...)` / `patch("time.sleep", ...)` only reaches code that looks the name up on the module at call time. Libraries that bind it at import (`from asyncio import sleep`) or as a default argument keep the real function — tenacity's `AsyncRetrying(sleep=sleep)` is the common case, so its backoff waits still sleep. Fix in the test by patching the class where the code under test looks it up, pre-bound to a no-op sleep — `patch("<module_under_test>.AsyncRetrying", functools.partial(AsyncRetrying, sleep=no_wait))` next to the existing `asyncio.sleep` patch (which still covers plain request-interval sleeps). Keep the retry-count and exception assertions untouched so the test still proves retries happen, then re-measure: randomized backoff (`wait_random_exponential`) makes the old timing vary run to run, so compare against several before-runs or the CI value.

## Naming an unreachable product-code wait

- Grep every retry/backoff/join site of the class first (`git grep -nE "join\(timeout=|\.wait\(|sleep\(|2 \*\*" <module>`): the same backoff formula usually appears twice with different indexing (`2 ** (n - 1)` vs `2**n`). One function, called with the offset that keeps each site's old values, is both the DRY fix and the patch point.
- Mutation-prove the tests still catch the behavior after the patch (remove the retry, remove the stop signal). Run each mutation under a hard timeout or in the background: a mutation that removes a stop signal can make a `join()` without timeout wait forever, which counts as caught but hangs the tool call. Restore the file in a `finally`.
- Payload-shipped modules (code serialized into a pod/Lambda) usually have a payload-equivalence test in the same tree; run the whole directory, not just the touched file.

## Narrowing a runtime `create_all` safely

- Table set = the models the service queries, their FK targets, **and every table a DDL trigger writes to**: grep the model module for `event.listen(<table>, "after_create", DDL(...))` — MySQL creates a trigger that references a missing table without error and only fails on the first write (`1146 ... doesn't exist`). Build the list from `Base.metadata.tables[model.__tablename__]` in one helper the code and the test fixtures both use (fixture `create_all` and the per-test truncate loop must iterate the same list, or truncate hits missing tables).
- Prove the list with a mutation: drop one table from it, rerun the hook tests, expect the 1146 failure, restore.
- Caller list for the PR body comes from one grep over every public entry point of the class (`git grep -lE "<Class>|<method1>|<method2>" <src>`), not from memory or the first page of hits; the list is usually 2–3× what you expect. Run the callers' test files too — one of them may be a slow test whose cost was this same `create_all` (it gets faster, confirm by timing it against the base ref).

## Suite-wide hermetic patches (cloud clients, library idle sleeps)

When the cause is a factory or library name many directories reach (a cloud-client factory, a library loop's `time`), patch it once for the session in the root `conftest.py`, next to the repo's existing "does not sleep" autouse fixtures:

```python
@pytest.fixture(autouse=True, scope="session")
def glue_catalog_is_unreachable():
    from botocore.exceptions import NoCredentialsError
    from <pkg> import catalog_meta
    def no_credentials(phase):
        raise NoCredentialsError()
    with pytest.MonkeyPatch.context() as mp:   # session scope: the `monkeypatch` fixture is function-scoped
        mp.setattr(catalog_meta, "clients", no_credentials)
        yield
```

- Raise the SDK's own "no credentials" error so callers take the fallback they already have for an unconfigured environment; tests that stub the client explicitly keep working because their function-level patch nests inside the session one.
- Grep every test that patches or calls the factory directly before choosing the patch point, and run those files plus the directories that hit the network.
- Add one guard test per patch (factory raises and the caller's accessor returns its fallback; the library module's `time.sleep` is a no-op while global `time.sleep` is not), then mutation-prove each guard by replacing that `mp.setattr` line with `pass` in a script that restores the file and checks it is byte-identical afterwards.
- Prove hermeticity on the whole suite, not the subset: run `./<tests>` with `scripts/boto_call_counter.py` before and after, both at the branch's base commit (the before-run in a throwaway worktree at that sha) — a before-run on an older base brings other commits' failures into the diff and every new local error then needs its own control run; the after count must be 0. Editing the root conftest cold-starts a testmon cache keyed on `**/conftest.py` once — say so in the PR.
- Make a session patch on a third-party module attribute version-tolerant: resolve the module from the patched function (`sys.modules[Cls.method.__module__]`) and patch only `if hasattr(module, name)`, else `yield` unpatched; the guard test `pytest.skip`s in that case. A bare `MonkeyPatch.setattr` raises `AttributeError` at session start when an upgrade moves or drops the name, which errors every test and blocks the upgrade branch the moment it picks up the commit. Before merging, check the in-flight upgrade: open/draft PRs touching the pinned requirements or the conftest (`gh pr list --search "<lib> in:title"`), and the upstream source of the target version (raw GitHub file at the release tag) for where the name lives.
- Positive control for the upgrade path without installing it: a scratch pytest plugin whose `pytest_configure` deletes the attribute (`del sys.modules[...].time`), run with `PYTHONPATH=<plugdir> pytest -p <plugin>` against the guard file — the fixed fixture must give `passed, 1 skipped`, the unguarded version `AttributeError`. Record that a real install was not run in `Not-tested:`.

## Profiling a whole work stream in one process

Per-file runs hide costs that repeat across files (the same large DAG factory built once per file, a client created per test). Profile the stream's subset in one pytest process, in CI order, from a driver script outside the repo:

```python
pr = cProfile.Profile(); pr.enable()
rc = pytest.main(["-p", "no:cacheprovider", "-q", "-m", "not dagbag", *targets])
pr.disable(); pr.dump_stats("stream.prof")
```

Then read it two ways: `cumtime` filtered to the repo's factory/helper names (call count × per-call seconds shows repeated construction), and `tottime` top 15 (I/O waits — SSL reads, socket receives, sleeps — surface here even when no single test looks slow). To find which tests reach a hot leaf, walk `pstats.Stats(...).stats[k][4]` (callers) upward until the first frame under the test tree; recursive cumtime double-counts across paths, so use it to rank, not to sum.

## Reproducing a Linux-only cost

When a cost shows on CI but not on macOS, A/B it in a Linux container with CI's own dependency file, toggling the suspect through a pytest plugin so the repo stays untouched:

- Scratch dir with the plugin module (e.g. `sqlite_nosync.py`) and a driver script that installs `requirements.dev.txt` with `uv pip install --system`, then runs the target files alternating `default` / `-p <plugin>` (with `PYTHONPATH=/probe`), 2 rounds, a fresh sqlite file per run, `--junitxml` per run.
- `docker run --rm --platform linux/<host arch> -v <worktree>:/src -v <scratch>:/probe:ro -v <out>:/out python:3.11-slim bash /probe/<driver>.sh`, in the background. Always pass `--platform`: an image tag already pulled for another arch runs emulated without failing, and emulation inflates CPU time so I/O effects shrink — grep the run log for `does not match the detected host platform` before trusting the numbers.
- Report per-file junit sums for both modes and both rounds; then re-run the actual branch (fix in conftest, no plugin) in the same container to confirm the shipped change reproduces the plugin's numbers.
- A container is not the CI runner: an fsync toggle worth ~35% in an arm64 OrbStack container did nothing on GitHub's runner. The container narrows a hypothesis; the PR's first CI run (same-base push run vs PR run, per-test `--durations` for the target files) decides whether the change stays. Say "reproduced in a Linux container, unconfirmed on CI" until then.

## Splitting a big setup into its parts

`python -m cProfile -s cumtime -m pytest -p no:cacheprovider -q <file>::<first test> 2>&1 | grep -E "create_all|get_container|wait_for_container|<fixture names>|ncalls"` gives seconds per fixture and per phase (container wait vs each `create_all`). Run it with the DB container stopped or not yet attached if you need the container share; on CI the first requester in the leg already paid it.

## Report shape

A table per file: CI seconds and test count, cause, verdict (fixable now / one-time cost / intended / needs a look). State the ranking method (log-timestamp estimate, which run) and its positive control, and keep unverified causes labelled as hypotheses.
